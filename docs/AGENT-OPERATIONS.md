# DSH Agent 操作手册：从下任务到途中干预

本手册面向使用 DSH-CTF-Skill 的操作者，说明如何让 agent 开始分析、选择单兵或编排、接收建议、继续原工作、暂停、恢复和交付结果。示例提示词可直接发送给主会话；把 `<附件目录>`、`<目标地址>`、`<工作ID>` 等占位内容换成实际值。

适用范围：当前 `main` 分支的接口与可选 CTF 预设，更新于 2026-10-25。旧版 v0.7.0 下载包不包含本手册描述的全部增量。CTF 预设仍属实验性；离线检查已覆盖交付和准入逻辑，真实 DSH 宿主兼容性需在所用环境验收。操作提示词不代表这些实验已经执行。

## 1. 先分清你在操作谁

你通常只需要给 DSH 主会话发送自然语言。主 agent 负责把请求转成实际工具调用，并反馈执行结果。下面的 `dsh_ctf`、`dsh_orchestration` 等是 agent 使用的工具名，不是终端命令，也不要求你手工输入 JSON。

| 工作方式 | 主 agent 的职责 | 你的建议发给谁 |
|---|---|---|
| 普通技能会话 | 按需加载 skill，在现有权限内分析与执行 | 当前会话；仅安装技能不保证主动加载 |
| CTF 单兵 `solo` | 选择相关技能，直接分析与执行 | 当前主会话 |
| CTF 编排 `orchestrated` | 计划、交接、监督、复核；具体执行交给 Solver | 当前主会话，并指明需要转交的 work / Solver |
| Solver | 在获得的材料、技能和工具范围内执行一项工作 | 通常让主 agent 通过编排接口转交 |
| Observer | 检查所交接的材料与论证，默认零工具 | 让主 agent 提供所需材料；实测另派 Solver |

CTF 预设在主会话模型调用前交付基础 skill，要求 agent 主动选模式和专业技能，并核对本会话实际钩子回执。它不预加载所有专业知识，不自动创建任务或派工，不扩大工具权限。

选用 `auto` 时，单题通常适合单兵，题库通常适合编排；复杂单题也可以分工。agent 应说明选择理由，用户明确偏好优先。固定为 `solo` / `orchestrated` 的 profile 需要调整配置才能反向选择。

## 2. 安装、启动与确认就绪

### 2.1 在 Linux / WSL 中安装 CTF 预设

以下是**在终端执行**的命令，在当前分支仓库根目录运行。需要自行准备 DSH、模型服务及专业工具；完整运行环境使用 Linux / WSL 原生文件系统，状态目录不要放在 `/mnt/`。Windows 用户应在 WSL 内运行此启动器。

首次体验建议使用独立 `DSH_HOME`。已有安装升级前，先按第 9 节暂停工作并确认收尾，再依据 [安装入门](QUICKSTART.md) 检查替换冲突；不要叠加重复插件或钩子。

```bash
export DSH_HOME="$HOME/.dsh-ctf"
export DSH_NATIVE_PACKAGE_ROOT="$(npm root -g)/@deepseek-ai/dsh"
python3 tools/setup.py --mode full --preset ctf
python3 tools/setup.py --mode full --preset ctf --apply
python3 tools/doctor.py --mode full --preset ctf
DSH_ANALYSIS_STATE="$DSH_HOME/analysis-state" python3 "$DSH_HOME/runtime/analysis-v1/session.py" health
python3 "$DSH_HOME/launch/ctf.py" --check
# 仅首次创建尚不存在的 profile 时使用 --from-default-profile
python3 "$DSH_HOME/launch/ctf.py" --profile ctf --from-default-profile web
```

后续在同样的环境变量配置下启动：

```bash
python3 "$DSH_HOME/launch/ctf.py" --profile ctf
```

安装默认偏好为 `auto`；需要固定模式时，在安装预览和应用命令中都增加 `--ctf-mode solo` 或 `--ctf-mode orchestrated`。安装器不配置模型密钥，不改已有 profile，不重启服务。`--check` 和 doctor 只检查配置/先决条件，不证明当前会话已加载 skill 或钩子成功。

### 2.2 启动后发给 agent

```text
先确认当前环境是否启用了 CTF 预设：检查 dsh_ctf status、analysis_session health；
如要编排，再检查 dsh_orchestration health。
报告当前模式偏好、已交付技能、当前上下文交付状态，以及本会话 hook_session 是否 ready。
尚未选择模式时明确说明，不要把“插件文件存在”当作“本会话已经就绪”。
如果工具不可用，指出缺失项和需要操作者处理的配置；先不要开始目标实验。
```

正常情况下，`dsh_ctf` 可用，钩子健康回执属于当前会话；首次模式可以是 `selection_required`，随后由 agent 选择。交付状态可能经历 prepared 到 delivered，刚选择技能后应在下一模型步核对。若模型步在准入时被阻止，agent 可能无法回答，应由操作者查看宿主日志中的 `[CTF preset blocked]`，按 [CTF 模式](CTF-MODE.md) 修复并维护重载。

仅安装 `skills` 时，没有上述运行工具也是预期情况。可让 agent 加载当前可用专业技能开展普通分析；需要强制交付和编排时再安装、启用完整预设。

## 3. 如何写一份能执行的任务

最好一次给出：目标、材料/入口、授权范围、交付物、关键限制。材料路径须能被 **DSH 所在环境**读取；WSL 和 Windows 路径不要混用。账号、令牌等用现有安全配置或受控引用交接，避免把秘密复制进提示词、报告或全体 Solver 的上下文。

### 通用任务模板

```text
目标：<希望得到的结果，例如恢复附件校验算法并验证候选输入>。
材料：<DSH 内可读的绝对路径>；相关题面：<内容或可读文件>。
目标入口/实例：<地址、实例标识；没有则写仅本地附件>。
授权范围：<允许分析的文件和目标，以及允许的操作>。
限制：<只读/不访问外网/不提交/不改原文件/并发上限；按实际需要写>。
交付：<脚本、报告、复现命令、候选及验证结果>，保存到 <输出目录>。

请先判断适合单兵还是编排，说明理由并选择相关 skill；已由宿主交付的材料无需重复加载。
在现有授权内自主执行，遇到权限、关键材料或范围冲突时报告具体阻塞。
保留原始证据和失败边界，区分观察、假设、本地验证与目标接受。
不自行增加总时限、尝试次数或必须并发的要求。
```

如果你有真实的截止时间、请求额度或并发要求，可以明确写入。当前编排机制没有兼容的 Solver 硬额度执行适配器，部分硬限额计划会阻止派发；提示词和工具计数不能代替全局请求拦截。无法保证额度时，让 agent 报告能力缺口，不要宣称已经启用硬限制。

## 4. 单题与单兵模式

### 4.1 一道逆向题：让 agent 从识别到验证

```text
请处理 <附件目录> 中的这道逆向题，题面位于 <题面文件>。
优先使用 CTF 单兵模式，先识别格式、架构、入口与校验路径，再按证据选择静态或动态方法。
根据需要选择 re-triage、ghidra-static、re-dynamic 等当前可用 skill；不要一次加载无关技能。
仅分析这些本地附件，原文件保持可追溯；需要运行样本时先核对当前隔离环境是否适合。
请交付可复现脚本、候选输入、原始验证结果和未解决问题，保存到 <输出目录>。
本地重放通过不等于远端或平台已接受。
```

### 4.2 未知附件类型：先识别，允许调整路线

```text
请分析 <附件目录>。目前不知道是流量、隐写、编码还是二进制题。
先使用单兵模式做格式和数据观察，再依据结果选择相关 skill。
如果后续发现值得独立验证的分支，请说明交接成本与收益，再按当前 auto 配置切换编排。
不要把初始猜测写成必须证明的结论，输出实际证据和可复现步骤。
```

复杂单题若希望一开始分工，可明确说：“使用编排模式，分别验证静态语义与运行行为；两者先从原材料形成结果，再比较差异。”技能选择不自动提供 Ghidra、Frida、Qiling、调试器或 shell；缺少能力时 agent 应说明缺项。

## 5. 题库与编排模式

### 5.1 题库任务书

```text
请处理 <题库目录>，题目清单在 <清单文件>，输出写到 <输出目录>。
使用 CTF 编排模式：先核对题目、附件和目标实例，建立唯一分析任务与记忆。
按题目/目标形成稳定的 objective_ref，只对可独立执行的工作派发 Solver。
最多同时运行 2 个执行型 Solver；这是我的并发要求，不是必须凑满的数量。
每项工作明确问题、成功标准、输入引用、skill_plan、execution_plan 和最小必要工具。
主会话负责监督、交接与复核；同一目标补材料优先复用原 work 和子会话。
按实际进展更新：已解决、候选待验证、阻塞、暂缓及原因。
不要把多个 Solver 的一致意见当作目标接受；未授权的平台提交先保留候选。
```

agent 应按实际需要完成 `init/bind → open 记忆 → enable → add/preflight → dispatch → 监督/复核`。只选择 `orchestrated` 不会自动执行这些步骤。题库中的不同目标应分别记录身份和证据范围；是否使用多个顶层任务应依目标与交付边界判断，不为绕开状态或数量限制另建任务。

### 5.2 指定一项工作，但不给结论

```text
请把 <问题或题目> 交给负责 <方向> 的 Solver。
问题是：<需要区分的解释或需要验证的性质>。
原始输入为 <可读引用>，成功标准是提供可核对证据，支持、否定、不确定或阻塞均可。
先查询当前 objective_ref 是否已有 work；已有就补充材料并续做。
请返回实际 task ID、work ID、职责、已授工具和派发状态。
```

记下 task/work ID，后续建议就能精确路由。任务 ID、工作 ID 和原生子会话 ID 是不同标识，编排的 `options.work` 使用实际 **work ID**。

## 6. 任务进行中提建议

### 6.1 发送建议的方式

直接在当前 DSH 对话继续输入，说明“补充建议，继续当前任务”。如果所用界面提供 Steer，可用它发送运行中建议。当前预设没有改造输入框：输入是否在下一步骤送达，取决于 DSH 界面如何调用原生接口；不能承诺所有普通输入都会即时 steer。

原生 `steer` 在最近可用模型步骤接收，不能瞬间打断一个正在阻塞的命令。编排中，你发给主会话的消息不会自动广播给所有 Solver；明确要求主 agent 通过 `dsh_orchestration steer` 转交，并反馈实际投递状态。

### 6.2 给当前单兵 agent 的技术建议

```text
补充建议，继续当前任务：
我观察到 <事实及原文/日志位置>。
我怀疑 <尚未验证的解释>，依据是 <理由>。
建议先做 <能区分解释的最小实验>。
如果结果为 <条件>，请重新考虑该假设。
如果已有证据排除了它，请说明依据，不必强行采用；保留当前有效进展。
```

具体示例：

```text
补充建议，继续当前任务：文件头的长度字段按小端解释时与文件大小更接近。
我怀疑当前解析使用了错误字节序。请先对同一组原始字节做大小端对照，
再检查多份记录是否同时满足边界；单个值合理还不能证明格式。
如果已有证据排除小端，请引用原始偏移和结果。
```

### 6.3 给编排中的特定 Solver

```text
请把以下建议通过 dsh_orchestration steer 转交给 work <工作ID>，保留其当前工作和子会话：
观察：<原始事实与引用>。
假设：<可能的解释>。
实验：<建议的区分实验>。
改判条件：<什么结果会推翻建议>。

请返回实际 work ID 和 guidance ID、投递是否成功；
后续报告 Solver 的理解/应用/反对或阻塞回执，以及实验结果。
如果建议不成立，保留反证。不要仅凭 delivered 或 applied 宣称验证成功。
```

不知道 work ID 时可以写：“先查当前协议分析工作的 work ID，再转交。”涉及多个工作时要求逐项列出接收者与回执，不要默认全体都收到。

### 6.4 给主 agent 的战略建议

```text
这是给主编排 agent 的策略建议，暂不直接转发给所有 Solver：
<我注意到的依赖、可能重复的工作或优先级问题>。
请结合当前证据、在途实验和交接成本判断是否调整派工，说明取舍。
如果需要改变某个 Solver 的任务，再用对应工作接口明确交接。
```

### 6.5 如何读建议回执

| 回执/状态 | 能说明什么 | 后续应核对什么 |
|---|---|---|
| queued / delivered | 宿主已排队或投递 | 是否在后续步骤被领取 |
| seen | 原生会话已领取消息 | Solver 是否理解其适用范围 |
| understood | Solver 自报理解 | 是否有实际实验 |
| applied | Solver 自报已应用 | 真实工具反馈与产物 |
| evaluated | Solver 自报已评价 | 实验是否能区分解释、结论范围 |
| disagreed | Solver 给出反对理由 | 理由及证据是否充分 |
| blocked | 无法应用 | 缺材料、工具、权限还是环境 |

独立对照工作有额外限制：不接受带结论的技术指导，续做只允许 `neutral:true`，不能夹带其他工作结论或替换技能计划。可先请求检查点或读取结果；需要带方向的新实验时，明确另派有来源说明的普通工作，保留原独立结果。

## 7. 查进度、补材料与原会话续做

### 7.1 查进度，不强迫换线

```text
请汇报当前进度，保持任务继续：
列出各 work 的状态、最近实际证据、在途命令或等待原因、阻塞及下一步。
区分正在计算、缺少近期反馈、空闲待续做和已返回；不要把耗时本身当失败。
只在需要核查的工作上读取 trace/结果；关键结论给出可追溯引用。
```

`trace` 仅是近期工具结果的有界预览，不是完整执行日志；长结果和状态须按返回游标/版本分页，不能把第一页或摘要当成全文。

### 7.2 请求保存进度，不打断有效实验

```text
请给 work <工作ID> 发 request_checkpoint，保存当前证据引用、未解决问题、
资源状态和下一步实验。暂不要求改变路线；如果当前命令阻塞无法马上保存，请如实说明。
```

### 7.3 补充文件，让原 Solver 继续

```text
新增材料位于 <DSH 可读绝对路径>，内容是 <来源与用途>。
请先确认负责 <目标> 的原 work，再通过 followup 继续同一子会话。
核对它是否有读取新材料的工具和权限；新材料不自动扩大其工具范围。
如需增加专业知识，在允许的空闲状态更新 skill_plan，并验证实际交付。
请说明新材料修订了哪些旧结论，保留原始证据和结果版本，返回后重新复核。
```

同一工作续做保留子会话身份和历史。旧结果若已经被其他工作依赖，需先处理依赖或明确另建工作；不要静默替换已采用的输入。已经取消或释放的工作不保证能用 `followup` 恢复，按第 9 节判断。

## 8. 更新约束与切换目标

### 8.1 收紧约束：明确这是指令

```text
约束更新，从现在起禁止向远端发起新请求，只允许分析现有本地材料。
这是用户限制，不是可选技术建议。
请将该约束写入当前任务并通知所有相关 Solver，停止/取消不符合约束的在途执行，确认收尾。
列出已通知和仍未确认的 work、可能尚未停止的操作；不要只发送 steer 就报告已停止。
```

新约束由 agent/工具执行路径落实，不是输入文本自动变成全局网络防火墙。已经发出的请求无法撤回；收尾不明时必须报告。放宽先前明确限制也应由你清楚写明范围和来源；技术建议本身不解除用户禁止事项。

### 8.2 目标实例更新

```text
目标实例已经重建，新入口是 <地址>，实例标识/依据是 <信息>。
请先停止旧实例相关的在途执行并确认收尾，再登记新的目标代次。
复核旧 cookie、连接、PID、地址和动态偏移；可复用的静态证据注明文件哈希与条件。
不要因为地址相同就认为仍是原实例，也不要把旧实例的成功当成本次接受。
```

## 9. 暂停、取消、恢复与切换模式

### 9.1 暂停整个编排

```text
请暂停当前编排，停止在途工作并确认原生收尾，保存已有证据与未决项。
报告每项工作的最终状态、仍存活的自有资源和 cleanup_unknown。
现在不要继续派发或自动恢复；也不要清理其他任务或共享服务。
```

`pause` 会取消在途执行，已返回结果保留；它不是冻结进程后可原地继续的暂停。检查点请求可能来不及在阻塞命令结束前保存。`cleanup_unknown` 表示不能确认收尾，不能报告“全部已停止”。外部进程和共享资源还须核对真实身份。

### 9.2 只取消一项工作

```text
请取消 work <工作ID>，原因是 <原因>。
确认其子代理和登记的自有后台资源收尾，保留已保存报告与日志，其他工作继续。
不要按端口、进程名或模糊路径批量清理共享资源。
```

### 9.3 继续暂停的编排

```text
请检查当前暂停任务的状态、原目标代次、用户约束、证据与资源。
确认旧工作已完全收尾且当前作用域有效后，再 resume。
对仍可续做的空闲 work 使用 followup；对已取消/释放且无法续做的工作，
明确新建工作并交接旧检查点、证据和未完成项，不要声称恢复了未保存的推理或进程。
先报告恢复计划，再在当前授权内继续。
```

`resume` 只恢复编排可用状态，不自动重放原实验。宿主退出后的 `recover` 只恢复元数据；原宿主仍活着时应在原宿主暂停/取消，不能强行接管。缺少外部资源状态时先核对再继续。

### 9.4 单兵与编排切换

```text
请将当前单兵任务切换为编排模式。
保留唯一任务、已有证据和目标代次，选择相关 skill，
再按 init/bind、记忆 open、enable 和工作计划完成必要设置。
只有可独立执行的分支才派 Solver；报告实际派发情况。
```

```text
请将当前编排切换为单兵。
先停止相关执行、确认收尾并 disable 当前编排，再通过 dsh_ctf select 选择 solo 及所需技能。
遇到 cleanup_unknown 或固定模式配置冲突时说明阻塞，不跳过检查。
模式切换后从已有证据继续，不把“选了模式”当作“工作已停止”。
```

## 10. 如何要求可信的结果

### 10.1 复核重要结论

```text
请复核 <结论或 work ID>：区分观察、推断和假设，核对原始输入、工具结果、
目标代次、干预条件及实际排除范围。
若它决定是否放弃重要路线，且证据仍薄弱，选择有价值的不同证据或方法验证。
仅检查论证可交给零工具 Observer；需要读文件或实验时派最小工具范围的 Solver。
不要把同模型一致意见、成功返回或指导回执当成独立验证。
```

### 10.2 完成或有边界地交付

```text
请按我的原交付范围整理最终结果：
给出结论、可复现脚本/命令、原始证据引用、验证对象与代次、干预条件、未决项和资源收尾状态。
候选 flag、本地校验通过与平台接受分别标明；未授权提交时不要自行提交。
若目标尚未达成，说明实际进展、阻塞和最有价值的下一步，不标记为已完成。
如交付范围已达成，按当前结果版本复核并记录最新完成处置，再结束编排与总任务。
```

编排 `review=adopted` 只表示主 agent 采纳结果，不等于目标接受。`finish` / `disable` 结束编排阶段也不证明用户目标完成。已启用过编排的任务要标为 complete，需最新版本的完成处置、实际范围和证据，再按顺序收尾；详见 [目标处置与完成](../skills/analysis-orchestration/references/resolution.md)。

## 11. 常见故障与处理提示词

| 现象 | 处理方式 |
|---|---|
| 没有 `dsh_ctf` | 确认使用当前分支的完整 CTF 预设启动器；仅技能模式不会提供它 |
| 已有技能文件却拒绝执行 | 核对当前作用域可调用性、必读参考、材料大小和上下文实际交付；文件存在不等于已交付 |
| 刚 select 就执行被拒 | 让下一模型步完成新技能正文交付，不在同批工具中绕过准入 |
| `hook_session.ready` 不成立 | 查本会话启动/最近钩子错误和 adapter 版本；不要复制其他会话回执 |
| `[CTF preset blocked]` 后 agent 无法回复 | 操作者检查宿主日志、材料或配置，维护重载后继续；提示词无法越过模型步准入 |
| 主编排不能运行 shell | 由具备相应工具的 Solver 执行，或按正常收尾流程切换单兵 |
| Solver 不能读取新附件 | 核对 DSH 环境的路径、实际授权工具和文件权限；引用路径不自动授予读取能力 |
| 发了建议一直没结果 | 区分主会话尚未处理、未转交、排队未领取、在途命令阻塞和实际实验未完成 |
| 独立对照拒绝 steer | 保留独立边界，用中性续做或先审结果；不要转成普通指导绕过契约 |
| 结果或签名过期 | 重新读当前状态和完整结果版本后复核；不要盲重试旧 signature |
| `cleanup_unknown` | 核对原生子会话和精确资源身份，未确认前保持未收尾状态 |
| 模式固定，无法反向选择 | 操作者按维护流程调整偏好为 auto 或目标模式，不要求 agent 忽略 profile |

用于诊断的通用提示词：

```text
请根据实际错误诊断当前阻塞，引用工具名、action、错误和当前状态。
区分配置缺失、权限不足、材料未交付、目标失效、执行未收尾及接口不兼容。
先做现有权限内的只读检查；需要操作者改配置或补材料时，给出最小具体步骤。
不要通过换会话、绕开守卫或伪造健康回执继续执行。
```

## 12. 工具调用速查：给需要精确控制的人

以下 JSON 是 **agent 调用指定工具的参数示例**，不是 shell 命令。实际 ID、版本、引用、工具名必须从当前返回值取得；先查询工具 schema。此节集中展示干预动作，完整派单与完成字段以对应 skill / schema 为准。

### 模式与健康

工具 `dsh_ctf`：

```json
{"action":"status"}
```

```json
{"action":"select","mode":"solo","reason":"单题先做附件识别","skill_plan":{"required":[{"name":"re-triage","reason":"核对文件类型与架构"}]}}
```

工具 `analysis_session`：

```json
{"action":"health"}
```

工具 `dsh_orchestration`：

```json
{"action":"health"}
```

```json
{"action":"schema"}
```

### 查看与纠偏

以下均为工具 `dsh_orchestration`：

```json
{"action":"status","task":"TASK_ID"}
```

```json
{"action":"trace","task":"TASK_ID","options":{"work":"WORK_ID"}}
```

```json
{"action":"steer","task":"TASK_ID","options":{"work":"WORK_ID","guidance":{"observation":"长度字段按小端解释时更接近原文件大小，尚未核对全部记录","hypothesis":"可能使用了错误字节序","experiment":"对原始字节做大小端对照，再检验多条记录边界","reconsider_if":"其他记录或原始校验不支持小端解释","evidence_refs":["实际原始证据引用"]}}}
```

```json
{"action":"request_checkpoint","task":"TASK_ID","options":{"work":"WORK_ID","reason":"保存当前证据、阻塞和下一步，暂不改变路线"}}
```

```json
{"action":"followup","task":"TASK_ID","options":{"work":"WORK_ID","message":"补充材料见实际可读路径，请在原授权内核对并修订旧结论"}}
```

独立对照仅使用以下中性续做，不附自由文本或替换技能计划：

```json
{"action":"followup","task":"TASK_ID","options":{"work":"WORK_ID","neutral":true}}
```

### 回执

工具 `dsh_solver_feedback`，仅由收到指导的活跃 Solver 使用，主 agent 不能代填：

```json
{"action":"ack","guidance_id":"GUIDANCE_ID","status":"understood","reason":"先核对原字节及多条记录，再判断字节序","evidence_refs":[]}
```

后续实际实验结果通过 progress 或对应 evaluated / disagreed / blocked 回执报告。主 agent 核对真实证据后再形成结论。

### 暂停、取消和恢复

以下均为工具 `dsh_orchestration`：

```json
{"action":"pause","task":"TASK_ID","options":{"reason":"用户要求暂停，确认所有在途工作收尾"}}
```

```json
{"action":"cancel","task":"TASK_ID","options":{"work":"WORK_ID","reason":"用户取消本分支，保留已保存证据"}}
```

```json
{"action":"resume","task":"TASK_ID"}
```

```json
{"action":"disable","task":"TASK_ID","options":{"reason":"确认执行收尾后解除编排，准备切换单兵"}}
```

原生开发接口还有 `Agent.steer()`、`Agent.followup()` 和 `Agent.inject()`：steer 面向最近可用步骤，followup 排入普通后续回合并唤醒，inject 只注入下一步骤上下文、不唤醒空闲 agent。它们不是用户聊天命令；对受监督 Solver 应使用编排接口，保留生命周期、范围检查和指导回执。

## 13. 一段完整对话示例

下面是一段操作模板，示例中的路径和 ID 都应以实际值替换。

**你：启动任务**

```text
请分析 /home/me/ctf/protocol-01，题面在 README.txt，输出到 /home/me/ctf/out/protocol-01。
仅本地分析，不访问远端，不修改原始抓包。请主动选择模式和相关 skill，恢复可验证的消息结构。
```

**agent 应做：** 核对就绪和材料，说明模式理由，选择相关技能；读取原始数据，区分传输片段与应用消息。若使用编排，报告实际 task/work ID。

**你：途中提出假设**

```text
补充建议：第 4 到 7 字节可能是小端长度；单个包吻合还不够。
请用多条完整记录验证，留意 TCP 分段。如果由 Solver 负责，请通过 steer 转交并给我 guidance ID。
```

**agent 应做：** 转交给正确 work 或在单兵会话评估；报告排队/领取状态，随后提供实验与回执。发现反证时修订解释。

**你：补材料**

```text
我新增了 /home/me/ctf/protocol-01/sample-b.pcap，请沿用原目标的 work 续做。
核对它与原抓包的来源和连接实例，判断哪些结论可跨样本成立。
```

**agent 应做：** 检查读取能力和原工作状态，适当 followup；新结果按版本重新复核，不把两份抓包简单拼成同一连接。

**你：要求交付**

```text
请交付当前可验证的字段表、解析脚本、运行命令、原始偏移引用和仍不确定的部分。
我的目标仅为本地协议分析报告，不要求连接服务器或取得 flag。
按这个范围复核完成状态，确认自有资源收尾后结束。
```

**agent 应做：** 按限定范围交付；若报告范围已完成则登记最新处置并收尾，若仍缺必要证据则明确未达成和阻塞。
