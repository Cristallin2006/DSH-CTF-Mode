# Linux 权限边界：配置、凭据与漏洞前提

根据目标和当前身份，按需观察 sudo 规则、SUID/SGID、capabilities、计划任务、服务参数和关键文件/父目录权限。配置与凭据问题可以低成本验证，但不存在通用“90%”比例或固定路线顺序。

```bash
id
sudo -l
getcap /KNOWN/BINARY
stat /KNOWN/SCRIPT
systemctl cat KNOWN_SERVICE
```

| 线索 | 需核对的成立条件 |
|---|---|
| sudo NOPASSWD | 允许的完整命令、参数、runas、环境过滤与交互限制 |
| SUID/SGID | 文件拥有者、实际挂载策略、调用链与降权行为 |
| capability | capability 集合、进程继承/解释器和命名空间；不只看一个标记 |
| 可写脚本/目录 | 谁会读取/执行、可达时机、参数和可替换范围 |
| cron/systemd | 实际启用状态、执行者、绝对路径/环境与重载条件 |
| 容器/管理组 | daemon 权限、挂载、user namespace 与目标是否要求跨宿主边界 |

工具配方（如 GTFOBins）只用于匹配已确认的命令/版本与权限前提；自定义 SUID 程序可转 re-* 或 vuln-audit 分析。不要把版本字符串当漏洞成立证明，发行版回补、架构、内核配置和实际原语均需核对。

变更关键文件、服务或账户前确认当前目标需要、影响和恢复方式，不把添加 UID 0 用户、修改 passwd 或挂载宿主根目录写成默认流程。凭据验证只针对有证据关联且在范围内的账户。

容器内 root、主机 root 与逃逸是不同结论；单看 /proc/1/cgroup 也不能覆盖所有容器识别场景。交付实际身份/能力、证据与剩余边界，卡住时重新比较前提和新实验的信息价值，不使用固定五分钟切换门。
